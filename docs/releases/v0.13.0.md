## 这一版回答的问题

用户问「拍照场景为什么不用 Lux3D 做」。核实后的结论是：**Lux3D 是单物件文生 3D，适合近景道具，不适合整间布景**——整间布景需要精确台面高度、0.6m 半径通透、可重打光/换背景色、体积可控，这些是程序化的强项。用户选择了「混合试点」：**程序化搭空间骨架，Lux3D 出近景道具**。

## 实现

- **`app/src/data/props.ts`**：`PROP_MODELS`（url / displayHeight / rotation）与中文名；`candle 0.12m`、`coffee-set 0.085m`、`table-lamp 0.45m`、`dried-bouquet 0.28m`。
- **`app/src/three/decor/scene-props.ts`**：运行时加载 + 归一化（先姿态修正、再按包围盒等比缩放到 displayHeight、水平居中、底面压到 0）、同 id 模板缓存、多实例 clone、`placement.height` 覆盖后重新落地、加载失败静默回退、按布景首次可见才加载（避免首屏把 4.2MB 道具全拉下来）、销毁时清理缓存。
- **三个布景**：`scene-festive.ts`（2 支蜡烛 GLB，程序化烛台隐藏但保留）、`scene-living.ts`（台灯与干花 GLB，`living-lamp-light` 点光保留并挪到新灯罩内 1.04m）、`scene-cafe.ts`（杯碟 GLB，隐藏 8 个程序化杯碟勺节点）。
- **`BouquetScene.ts`**：`syncPhotoSet()` 里对可见布景调用 `activateSceneProps()`；`dispose()` 先 `detachSceneProps()` 阻止迟到模型再挂，再释放并清缓存。
- **`app/scripts/v13-scene-props.mjs`**（新）：20 项验证，含断网拦截 GLB 的兜底路径。

## 已知边界与未做

- **整间布景仍程序化**：设计上的取舍，不是省积分。整间空间若要「生成」，对应接口是 `world/v1`（3DGS 世界生成/重建），输出不是可编辑 mesh 且未接入现有 Three.js 渲染管线；本轮没有尝试验证。
- 道具是**烘焙材质**：不能跟随作品配色/换色，不能像程序化道具那样参数化调节；节日蜡烛的火焰仍是程序化自发光（GLB 只有裸烛芯）。
- 生成侧瑕疵：`dried-bouquet` 贴图降档后 2× 近看花瓣偏软（取舍与恢复 1024 约 +160KB 的备选写在 manifest 备注里）；`table-lamp` 底座自带一条细电源线，默认机位不可见；`coffee-set` 是空杯（无咖啡液面）。
- 三件布景的三角面明显上升：节日暖光 68k、家居客厅 70k（含两件 GLB）、咖啡馆约 30k；只在拍照阶段可见，未测移动端/低端机帧率。4K 导出、真实设备帧率仍未验收。
- 断网兜底只验证了「拦截单个 GLB」，没有模拟弱网下的逐步加载观感。
